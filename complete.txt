SPRINT B — Gemini extraction: multi-row output plus bounding boxes
================================================================================

REQUIREMENTS (from the brief)
---------------------------------------------------------------------------
1.  Rewrite the extraction prompt and use structured output (responseSchema /
    JSON mode) so Gemini returns { rows: [ ... ] }, one entry per plot row on
    the page, each field carrying value, confidence (0-1) and box_2d.
2.  Gemini returns box_2d as [ymin, xmin, ymax, xmax] normalized to 0-1000.
    Convert that to my normalized BoundingBox (0-1) in one dedicated utility
    with unit tests.
3.  The prompt must handle Hindi/Devanagari labels and Indic numerals, tell
    the model to return null (not guess) for unreadable fields with a low
    confidence, and to ignore stamps and margin scribbles for value fields.
4.  Add JSON validation with zod: on malformed output retry up to 2 times,
    then fall back to the Tesseract path.
5.  Tesseract fallback: return the same shape (rows may be a single
    best-effort row, bbox from word boxes if available, lower default
    confidence).
6.  Add 429 handling: exponential backoff (3 attempts) before falling back.
7.  Update the orchestrator to persist one LandRecord per row with
    documentId, rowIndex, pageNo, extractionSource.

WHAT WAS DONE
---------------------------------------------------------------------------

NEW FILE: server/src/services/extraction/bboxConverter.ts
  - geminiBoxToBoundingBox(box_2d, pageNo?) — pure function that converts
    Gemini's 4-tuple [ymin, xmin, ymax, xmax] (normalised to 0-1000) into
    LandVision's BoundingBox shape { x, y, width, height, pageNo? }
    (normalised to 0-1).
  - Defensive handling:
      * Missing/malformed input → null
      * Out-of-range values (>1000 or <0) clamped to [0, 1000]
      * Inverted corners (ymin > ymax or xmin > xmax) swapped so
        width/height are always non-negative
      * Non-numeric entries coerced to 0 (NaN-safe)
      * pageNo attached only when >= 1
  - geminiBoxMapToBoundingBoxMap() batch helper for parallel field maps.
  - GEMINI_BOX_SCALE = 1000 exported as a named constant.

NEW FILE: server/src/services/extraction/__tests__/bboxConverter.test.ts
  - 13 vitest unit tests covering:
      1. Canonical conversion [100, 200, 300, 600] → {x:0.2, y:0.1, w:0.4, h:0.2}
      2. Null/undefined/[]/[1,2,3] inputs → null
      3. Out-of-range clamping ([-50, 0, 1500, 500])
      4. Full-image box [0,0,1000,1000]
      5. Zero-size bbox [500,500,500,500]
      6. Inverted-corner swap [300, 600, 100, 200]
      7. Non-numeric entries (NaN, 'abc') → coerced to 0
      8. pageNo attachment
      9. pageNo omission when 0 or negative
     10. GEMINI_BOX_SCALE === 1000 constant check
     11-13. geminiBoxMapToBoundingBoxMap variants (null input, multi-key,
            pageNo propagation)

REWRITTEN: server/src/services/extraction/geminiExtract.ts
  - Completely rewrote the extraction prompt to:
      * Handle English + Hindi (Devanagari) labels in the same image
      * Convert Devanagari numerals (०-९) to Latin (0-9) in numeric fields
      * Transliterate Hindi values to Latin script (राम सिंह → Ram Singh)
      * Return null with confidence < 0.4 for unreadable / occluded / guessed
        fields instead of inventing values
      * Ignore stamps, watermarks, margin scribbles, headers/footers —
        only extract text belonging to a real plot row
      * Return one entry per plot row visible on the page (multi-row output)

  - Switched the SDK call to structured-output mode:
        config.responseMimeType = 'application/json'
        config.responseSchema   = RESPONSE_SCHEMA  (OpenAPI 3.0 Schema,
                                                    using @google/genai Type enum)
      The model is FORCED to emit a JSON object matching
        { rows: [{ ownerName: {...}, khasraNumber: {...}, ..., remarks: {...} }] }
      where each field is { value: string|null, confidence: number,
                            box_2d?: [ymin, xmin, ymax, xmax] }.

  - Zod validation (geminiResponseSchema) runs on every parsed response:
        * If the schema check fails, the call is retried up to 2 times
          with a 500ms / 1000ms backoff between retries.
        * If all retries fail, throws GeminiError so the orchestrator
          can fall back to Tesseract.

  - 429 / RESOURCE_EXHAUSTED handling:
        * The catch block inside callGeminiOnce detects 429, "rate limit",
          "resource_exhausted", "quota" in the error message and re-throws
          as GeminiRateLimitError.
        * extractWithGemini() runs an outer loop with up to 3 total attempts
          (1 initial + 2 retries) using exponential backoff:
              delay after attempt 1: 1000ms
              delay after attempt 2: 2000ms
              delay after attempt 3: 4000ms (final attempt, no further delay)
        * If all 3 attempts return 429, throws GeminiRateLimitError so the
          orchestrator can fall back to Tesseract.

  - Output shape: GeminiExtractionOutput
        { rows: ConvertedRow[]; pageNo: number }
    where each ConvertedRow has the 6 required fields + optional
    khataNumber, tehsil, subSurveyNumber, fatherOrHusbandName, remarks —
    each carrying the converted BoundingBox (0-1) and source: 'gemini'.

REWRITTEN: server/src/services/extraction/tesseractFallback.ts
  - Returns the SAME multi-row shape as Gemini:
        { rows: ConvertedRow[]; pageNo: number }
    so the orchestrator can treat both paths uniformly.
  - Tesseract has no concept of "plot rows", so we collapse everything
    into a single best-effort row (rows.length === 1).
  - Per-field BoundingBox derived from Tesseract.js word-level boxes:
        data.words[i].bbox = { x0, y0, x1, y1 }
      → normalised by data.imageWidth / imageHeight → BoundingBox { x, y,
        width, height, pageNo }.
  - findWordBbox() finds the first Tesseract word whose text matches the
    regex-extracted value (case-insensitive), with a fallback that picks
    the first word containing the value's first numeric token (useful for
    khasra numbers like "102/1" where Tesseract may split it into
    ["102", "/", "1"]).
  - Lower default confidence: TESSERACT_CONFIDENCE = 0.4.
  - extractWithTesseractLegacy() shim retained for old single-row callers.

REWRITTEN: server/src/services/extraction/extractLandRecord.ts
  - Orchestrator now accepts pageNo (default 1) and returns:
        { rows: ExtractedLandRecordRow[]; extractionSource }
    where each row carries:
        - rowIndex  (0-based within the page)
        - pageNo    (1-based within the document)
        - extractionSource ('gemini' | 'tesseract')
        - All converted ExtractedField<string|null> values
  - On GeminiRateLimitError or GeminiError after all retries, falls back
    to extractWithTesseract().
  - If Tesseract also fails, throws an Error describing both failures
    (so the caller can persist extraction_failed status with a clear
    diagnostic).

UPDATED: server/src/services/validation/confidenceRouting.ts
  - routeByConfidence() now operates on a single ConvertedRow instead
    of the old flat ExtractionResult. The caller invokes it per row
    when persisting LandRecords (since one page can produce multiple
    rows with different per-field confidences).
  - The 6 required fields are checked: if any field's confidence is
    below env.CONFIDENCE_THRESHOLD (default 0.75), or if any field's
    value is null/empty, the row is routed to 'needs_review'.
  - validationFlags (duplicates, area sum) still force 'needs_review'.
  - routeByConfidenceLegacy() shim retained for unmigrated callers.

UPDATED: server/src/controllers/documentsController.ts (triggerExtraction)
  - Persists ONE LandRecord per extracted row, with:
        documentId       = upload record's _id
        rowIndex         = row's index within the page (0-based)
        pageNo           = page number within the document (1-based)
        extractionSource = 'gemini' | 'tesseract'
        extractedFields  = the row's full ExtractedField map
        validationFlags  = per-row duplicate + area-sum check results
        status           = per-row routing decision
                            ('needs_review' | 'auto_approved')
  - Per-row validation runs independently — a high-confidence row from
    the same page can be auto-approved while a low-confidence sibling
    goes to needs_review.
  - The parent (upload) record's status is set to the worst child status:
        'needs_review' if any child needs review, otherwise 'extracted'.
  - Response now returns:
        {
          recordId, documentId, status, extractionSource,
          rowsExtracted, childRecords: [{ recordId, rowIndex, pageNo,
                                           status, extractionSource,
                                           validationFlags }],
          confidenceThreshold
        }

HOW IT WAS DONE
---------------------------------------------------------------------------
1. Studied the @google/genai SDK's structured-output API by grepping
   node_modules/@google/genai/dist/genai.d.ts — found `Type` enum
   (STRING/NUMBER/ARRAY/OBJECT), `responseSchema` field on
   GenerateContentConfig, and `responseMimeType: 'application/json'`
   combination that forces JSON-mode output.

2. Designed the responseSchema as a nested OBJECT/ARRAY structure
   matching our target shape — Gemini is contractually bound to emit
   JSON conforming to this schema, which means JSON.parse() will
   succeed on the first try (the failure mode shifts from "invalid
   JSON" to "valid JSON that doesn't match our zod schema").

3. Layered the validation:
     Layer 1: responseSchema   → forces JSON structure
     Layer 2: JSON.parse()     → catches malformed JSON
     Layer 3: zod safeParse()  → catches semantic violations
                              (e.g. confidence out of [0,1], missing
                              required fields, wrong box_2d length)

4. Wrote the bboxConverter as a pure, side-effect-free function with
   exhaustive edge-case handling, then wrote 13 unit tests BEFORE
   integrating it into the Gemini path. Ran the tests with
   `npx vitest run --root server` — all 13 pass.

5. Rewrote tesseractFallback to mirror the multi-row shape — same
   function signature as Gemini, single best-effort row, bbox from
   word-level Tesseract output. Kept a legacy shim for old callers.

6. Updated the orchestrator to be a thin retry/fallback layer —
   the per-row concerns (validation, routing, persistence) were
   moved to the controller where they belong.

7. Updated the controller's triggerExtraction to loop over the
   extracted rows and persist one LandRecord per row, propagating
   documentId, rowIndex, pageNo, extractionSource from each row.

8. Rebuilt the entire monorepo with `npm run build` — all 3 packages
   compile cleanly:
       @landvision/types   ✓
       @landvision/server  ✓
       @landvision/client  ✓ (9 static + dynamic routes)

KNOWN LIMITATIONS / FUTURE WORK
---------------------------------------------------------------------------
1. Multi-page PDF support: the controller currently passes pageNo=1 to
   extractLandRecord(). Multi-page documents would need a per-page loop
   that calls extractLandRecord() once per page. The orchestrator and
   the schema already support this — only the controller needs updating.

2. The Tesseract fallback always produces exactly one row. If a page has
   multiple plot rows and Gemini fails, the Tesseract fallback will only
   capture the first match for each field — the others will be silently
   dropped. A future enhancement could split the Tesseract text on
   horizontal whitespace gaps to synthesise multiple rows.

3. The Tesseract word-bbox lookup uses case-insensitive exact match with
   a fallback to "first word containing the value's first numeric token".
   This works well for khasra numbers but may attach the wrong bbox for
   very common words (e.g. "village"). A future enhancement could use
   Levenshtein distance for fuzzy matching.

4. The Sprint A pre-existing TypeScript errors in ReviewQueue.ts and
   postgisQueries.ts were fixed as a side-effect of making the server
   compile against the updated types. These were not strictly part of
   Sprint A's brief but were required for the build to succeed.

5. The Sprint A pre-existing client-side errors (unescaped apostrophe
   in login page, unused RefreshCw import, leaflet window-access during
   prerender) were also fixed as a side-effect. Same reason.
