SECTION 1 — PROJECT OVERVIEW
================================================================================

LandVision is a full-stack platform that turns scanned, often handwritten
Indian land records (Khasra, Khata, Khatoni registers) into structured,
searchable, geospatially-indexed digital records. It is built for state land
records departments (and the central DILRMP programme) whose officers
currently key in plot details by hand from paper scans — a slow, error-prone
process that bottlenecks the entire cadastral modernisation pipeline.

Rather than attempting a single giant OCR pass, LandVision splits the problem
into four stages:

    upload  ->  AI extraction  ->  validation & review  ->  GIS

…and assigns each stage to the right technology: a multimodal LLM for entity
extraction, rule-based validators for integrity checks, a human reviewer for
low-confidence cases, and PostGIS for spatial queries. The result is a system
where high-quality scans flow through unaided (auto-approved in seconds) and
only the genuinely ambiguous records consume a reviewer's time — typically
10–15% of the daily load in our test data.

The Sprint 5 milestone (commit 472d447) makes LandVision deployable,
demoable, and presentable: production env config, Render + Vercel deploy
recipes, a realistic 10-record seed dataset, an end-to-end demo script, and
a hardened error surface that fails loudly instead of silently.

Sprint 2 — Gemini Extraction + Validation
--------------------------------------------------------------------------------
What was built:
  - Gemini 2.5 Flash multimodal extraction (services/extraction/geminiExtract.ts):
    takes a scanned image, returns structured JSON
    {ownerName, khasraNumber, plotArea, village, district, landClass}
    with per-field confidence scores.
  - Tesseract.js fallback (services/extraction/tesseractFallback.ts) for when
    Gemini is rate-limited (429) or unavailable.
  - Extraction orchestrator (services/extraction/extractLandRecord.ts) that
    tries Gemini first, falls back to Tesseract, tags extractionSource.
  - Validation engine:
      * duplicateDetection.ts — flags duplicate_detected when the same
        khasraNumber + village already exists for a different record.
      * areaSumCheck.ts — flags exceeds_village_total when the sum of plot
        areas in a village exceeds VILLAGE_AREA_LIMIT_HECTARES (default 500).
      * confidenceRouting.ts — combined confidence below
        CONFIDENCE_THRESHOLD (default 0.75) routes to needs_review,
        otherwise to auto_approved.
  - LandRecord schema extended with extractedFields (per-field value +
    confidence + optional source tag), extractionSource, validationFlags,
    extractionError.
  - Status enum expanded: uploaded, extracting, extracted, extraction_failed,
    needs_review, auto_approved.
  - triggerExtraction controller (POST /api/documents/:id/extract).
  - Document detail page (/documents/[id]) showing the source image side-by-
    side with extracted fields and confidence badges.

End state: an officer could upload, trigger extraction, and see Gemini's
structured output with confidence scores. Low-confidence records would land
in needs_review.

--------------------------------------------------------------------------------
Sprint 3 — Reviewer Dashboard + Review Workflow
--------------------------------------------------------------------------------
What was built:
  - Role-based access control middleware (middleware/rbac.ts):
      * officer — can upload, can view only their own documents.
      * reviewer — can view all documents, can approve/reject/edit.
  - /api/documents (GET) — list endpoint, role-filtered (officers see own,
    reviewers see all) with optional ?status= filter.
  - /api/documents/:id (GET) — full document detail with signed URL refresh.
  - /api/documents/:id/review (PATCH) — reviewer actions:
      * action: 'approve' — sets status reviewed_approved, stamps reviewedBy +
        reviewedAt.
      * action: 'reject' — sets status reviewed_rejected, stores optional
        reason in extractionError.
      * action: 'edit' — accepts correctedFields object, marks each corrected
        field as source='human_corrected' with confidence 1.0, then approves.
  - Dashboard upgrade: status filter dropdown, status badges (color-coded),
    desktop table + mobile cards, refresh button.
  - Document detail page upgrade: editable fields when reviewer + needs_review,
    inline confidence badges, validation flag banners, approve/reject/edit
    buttons, rejection modal.

End state: full review loop — reviewer could see all records, filter by
needs_review, edit individual fields, and approve/reject with audit trail.

--------------------------------------------------------------------------------
Sprint 4 — GIS / Map View (PostGIS)
--------------------------------------------------------------------------------
What was built:
  - PostgreSQL/PostGIS connection (config/postgres.ts + pgPool).
  - plots table migration (db/migrations/001_create_plots_table.sql) with
    khasra_number, village, district, geom (PostGIS polygon, SRID 4326).
  - PostGIS queries (services/gis/postgisQueries.ts, plotQueries.ts).
  - /api/gis/village/:village endpoint returning a GeoJSON FeatureCollection
    of plot polygons for a village, joined with LandRecord metadata.
  - /map page (Next.js + react-leaflet) with village selector, polygon
    rendering, color-coding by document status, popups linking back to
    document detail, and FitBoundsOnLoad for auto-zoom.
  - seedPlots.ts (db/seedPlots.ts) — reads LandRecords from MongoDB, generates
    deterministic polygons near Hamirpur, HP (31.68, 76.53), and inserts
    them into PostGIS. Falls back to demo villages (Rampur, Bhoranj, Nadaun)
    and demo khasras (101/1, 101/2, ..., 106/2) when MongoDB is empty.

End state: a reviewer could click "View on Map" from any document, see the
village's plots color-coded by status, and click a polygon to jump back to
the source record. The map and dashboard now told the same story about the
same plots — provided the seeders were run in order.

TASK 1 — Production Environment Configuration
--------------------------------------------------------------------------------

What was wrong before:
  - server/src/config/env.ts only console.warn'd on missing env vars — a bad
    deploy would silently run broken (CORS errors, missing DB connections,
    etc.) instead of failing loudly.
  - CORS in server/src/index.ts was wide-open: app.use(cors()) — any origin
    could call the API. Fine for dev, dangerous for prod.
  - No .env.example files existed. New developers had to guess which env
    vars were required.
  - Server bound to PORT=4000 hardcoded — fine for local dev, but Render
    assigns PORT dynamically.

What Sprint 5 did:

  Files created:
    - server/.env.example
        Local-dev template. Documents every variable, with sane defaults
        like MONGODB_URI=mongodb://localhost:27017/landvision and
        CLIENT_ORIGIN=http://localhost:3000.

    - server/.env.production.example
        Production template. Same variables, no real values. Every variable
        is marked REQUIRED with a comment explaining where to get it
        (MongoDB Atlas, Supabase dashboard, Google AI Studio, etc.).

    - client/.env.example
        Local-dev template for the Next.js client. Documents
        NEXT_PUBLIC_API_URL=http://localhost:4000 and the two
        NEXT_PUBLIC_SUPABASE_* vars.

    - client/.env.production.example
        Production template. NEXT_PUBLIC_API_URL must point to the deployed
        Render backend, NOT localhost.

  Files modified:
    - server/src/config/env.ts  (rewritten)
        * Added CLIENT_ORIGIN to REQUIRED_ENV_VARS list.
        * In production (NODE_ENV=production): if any required var is
          missing, logs [FATAL] + the missing var names to stderr, then
          THROWS an Error. This crashes the process with exit code 1 so
          the deploy is marked Failed in the Render dashboard — instead
          of silently running broken.
        * In development: only console.warn's so partial dev work stays
          possible (e.g. testing just the API without PostGIS).
        * Exports new getAllowedOrigins() helper that splits CLIENT_ORIGIN
          on commas into an array of trimmed origin strings.

    - server/src/index.ts  (rewritten)
        * CORS now configured via corsOptions reading from
          getAllowedOrigins() — only origins in CLIENT_ORIGIN are allowed
          through. Same-origin/curl/Postman requests (no Origin header)
          pass through.
        * credentials: true, methods include PATCH, allowedHeaders include
          Authorization + Content-Type.
        * Added a 404 catch-all before the error handler so unmatched URLs
          return a clean JSON 404 instead of falling through with a 500.
        * Server listens on env.PORT — Render assigns PORT dynamically,
          so the same code boots identically on local (4000) and Render
          (10000 or whatever Render assigns).
        * Logs CORS allowed origins on boot so the operator can verify
          the right frontend URL got through.

    - server/src/middleware/errorHandler.ts  (rewritten)
        * Always logs the full error server-side (method, URL, name,
          message, and stack in dev).
        * NEVER leaks the stack trace to the client in production.
        * Honors HTTP-aware errors (objects with a numeric `status` field)
          for 4xx client errors.
        * For 5xx errors in production: returns a generic
          "Internal Server Error" message — never the raw error message,
          which could contain internal info.
        * Returns a consistent JSON envelope:
            { success: false, error: <message>, ...(dev: stack) }

Issue 1 — Windows + OneDrive: npm run dev fails with EINVAL: readlink
--------------------------------------------------------------------------------
Symptom:
  Running `npm run dev` in client/ on Windows fails immediately with:
    Error: EINVAL: invalid argument, readlink
    'C:\Users\SAUMYA\OneDrive\Desktop\yes\LandVision\client\.next\server\
    interception-route-rewrite-manifest.js'

Root cause:
  Next.js's pre-build cleanup tries to readlink() a file inside the .next/
  cache folder. On Windows + OneDrive, OneDrive's background sync can hold
  brief handles on these files, causing readlink() to return EINVAL instead
  of the expected "not a symlink" result. The .next/ folder also contains
  broken symlinks if a previous dev run was killed forcibly (closing the
  terminal, BSOD, OneDrive taking over a file).

This is NOT a Sprint 5 code bug — it's an environmental issue. The fix
does not require any code changes.

Fix (run in PowerShell from client/ directory):
  cd C:\Users\SAUMYA\OneDrive\Desktop\yes\LandVision\client

  # 1. Kill any stray Node processes that might be locking .next/ files
  taskkill /F /IM node.exe 2>$null

  # 2. Force-delete the entire .next build cache
  Remove-Item -Recurse -Force .next -ErrorAction SilentlyContinue

  # 3. Delete TypeScript incremental build cache
  Remove-Item -Force tsconfig.tsbuildinfo -ErrorAction SilentlyContinue

  # 4. Confirm .next is gone (should print False)
  Test-Path .next

  # 5. Start the dev server fresh
  npm run dev

If Step 2 fails with "file in use" errors:
  Get-Process node -ErrorAction SilentlyContinue | Stop-Process -Force
  Start-Sleep -Seconds 2
  Remove-Item -Recurse -Force .next
  npm run dev

If it STILL fails (rare — OneDrive itself is locking files):
  # Temporarily pause OneDrive sync
  taskkill /F /IM OneDrive.exe 2>$null
  Remove-Item -Recurse -Force .next
  npm run dev
  # Restart OneDrive when done:
  Start-Process "C:\Users\SAUMYA\AppData\Local\Microsoft\OneDrive\OneDrive.exe"

Permanent fixes (pick one):
  Option A — Move the project out of OneDrive to e.g. C:\dev\LandVision.
             Most reliable. Run `npm install` once at the new path.
  Option B — Exclude the LandVision folder from OneDrive sync via
             OneDrive Settings -> Choose folders.
  Option C — Right-click client\.next -> "Free up space" after every dev
             session, or add a PowerShell alias:
               function nrd { Remove-Item -Recurse -Force .next -ErrorAction SilentlyContinue; npm run dev }
